This area is about writing code that other people can read and change. It covers the daily habits of a programmer: naming, comments, style, refactoring, code review and work with old code.

## What it holds

- Naming: how to name variables, functions and types.
- Readable code: code that a reader understands quickly, and the habits that give it.
- Comments and documentation in code: what a comment must say, what it must not say, and doc comments.
- Code style and formatting: style guides, and formatters that apply a style for you.
- Code smells: signs in code that a design problem is likely.
- Refactoring: the catalogue of refactorings, each a small change that keeps behaviour.
- Code review: how to review code and how to answer a review.
- Technical debt: the cost of shortcuts, and how to track and pay it.
- Defensive programming: code that checks its inputs and fails clearly.
- Working with legacy code: how to change code that has no tests.
- Pair and mob programming: writing code with two or more people at one screen.

## What it does not hold

- Design at the level of modules and systems. It is in [Software design](/software-design/).
- Documentation tools and project documentation. They are in [Tools and workflow](/tools-and-workflow/) and [Software engineering process](/software-engineering-process/).
- Linters as analysis tools. They are in [Program analysis and verification](/program-analysis-and-verification/).
- Tests. They are in [Testing](/testing/).
